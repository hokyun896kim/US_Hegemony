# 한국 헤게모니 트리 (KR Edition)

미국판과 **같은 동결 스코어러**를 KOSPI·KOSDAQ에 적용한 버전.
핵심 지표는 하나다:

```
헤게모니 스프레드 = 영업이익 YoY(%) − 매출 YoY(%)
```

매출보다 이익이 빠르게 늘면 양수 — 가격결정력·고정비 레버리지가 작동 중이라는 신호다.
여기에 **분기 TTM**을 나란히 놓아 가속(막 붙는 중)과 피크아웃(꺾이는 중)을 가른다.

| 파일 | 역할 |
|---|---|
| `index.html` | 화면(루트). `./data/tree_kr.json` 을 읽는다 |
| `us.html` | 기존 미국판 화면 |
| `build_tree_kr.py` | 데이터 빌더 (yfinance 단일 소스, **API 키 불필요**) |
| `data/tree_kr.json` | 빌더 산출물. GitHub Actions가 매주 갱신 |
| `.github/workflows/update_kr.yml` | 주간 자동 갱신 + 개발 브랜치 스모크 빌드 |
| `tests/` | `index.html` 을 jsdom으로 띄워 눌러보는 스모크 테스트 |

## 실행

```bash
pip install yfinance

python build_tree_kr.py --selftest     # 네트워크 없이 로직·스키마 검증
python build_tree_kr.py --limit 40     # 빠른 확인
python build_tree_kr.py                # 기본 300종목

python -m http.server 8000             # file:// 로 열면 CORS로 막힌다
```

`--limit` 은 시가총액 상위 N종목, `--min-cap` 은 최소 시총(원, 기본 3000억).

## 파이프라인

1. **유니버스** — `yf.screen()` 으로 한국 상장사를 시총 내림차순 페이징.
   종목명·섹터·세부산업·PER·PEG를 여기서 함께 받는다(호출 몇 번이면 끝).
2. **재무** — 종목별 연간/분기 손익계산서에서 매출·영업이익을 뽑아 스프레드 계산.
3. **시세** — 50개씩 일괄 다운로드해 코스피 대비 상대강도(3M·6M), 갭위험, 52주 고점比.
4. **조립** — 세부산업/대섹터별 **중앙값**으로 트리를 만든다.

### 미국판은 SEC 차단을 안고 돈다 — 부분 갱신으로 받는다

미국 빌드는 18회 중 **17회가 SEC 403 으로 죽었다**. 전부 `Request Rate
Threshold Exceeded` 이고 **첫 요청부터** 막힌다. Actions 러너는 공유 NAT 출구
IP 를 쓰는데, 같은 IP 뒤의 다른 크롤러들이 이미 SEC 쿼터를 태워놓기 때문이다.
우리 쪽 속도를 초당 3건으로 낮춰도, 11분씩 두 번(총 22분) 기다려도 안 풀린다 —
우리가 만든 문제가 아니라서 그렇다.

**빌드가 죽는 지점은 딱 한 곳이었다.** `www.sec.gov/files/company_tickers.json`
— 티커맵을 받는 첫 요청이다. 정작 재무 데이터는 **`data.sec.gov`** 에서 오는데
그건 다른 호스트이고, 지금까지 한 번도 거기까지 가본 적이 없어 열려 있는지조차
몰랐다.

그래서 티커맵을 받아두고 재사용하도록 만들었다(`data/sec_tickers.json`).
동시에 캐시가 없을 때 `data.sec.gov` 를 한 번 찔러보고 결과를 로그에 남기게
했다 — 두 호스트의 차단이 별개인지 알아야 했기 때문이다.

**실측 결과 별개가 아니었다(2026-08-08 run #22):**

```
[!] SEC 403 — SEC.gov | Request Rate Threshold Exceeded
    URL: https://www.sec.gov/files/company_tickers.json
[진단] data.sec.gov 도 막혔습니다(HTTP Error 403: Forbidden)
       — SEC 전체가 이 출구를 거부합니다.
```

즉 **티커맵 캐시로는 안 풀린다.** 차단은 특정 경로가 아니라 출구 IP 단위이고,
SEC 도메인 전체가 막힌다. 캐시와 진단은 그대로 두지만(공짜이고, 다음에 부분
차단을 만나면 쓸모가 있다) 이게 해결책은 아니다. 지금으로선 **새 출구 IP 를
뽑는 것 말고는 방법이 없고**, 그게 주간 크론과 백업 슬롯이 하는 일이다.

그래도 안 되면 통째로 실패하는 대신 **가격층만 갱신**한다(`refresh_prices.py`).

| 출처 | 항목 | 실제 변경 주기 |
|---|---|---|
| SEC | 매출·영업이익 YoY, 스프레드, 분기TTM, 가속, IR 링크 | 분기 |
| 야후 | RS3M·RS6M, 52주 고점比, 갭위험, 현재가(→PER) | 매일 |

선취매 판정(`priceIn`)이 쓰는 값은 전부 아래쪽 — 야후에서 온다. 그래서
펀더멘털을 지난 회차 값으로 두고 가격층만 새로 받아도 판정은 최신이 된다.
대신 **날짜를 갈라서 표시**한다: `updated`(가격 기준일)와
`fund_updated`(펀더멘털 기준일)가 다르면 화면 상단에 경고 배너가 뜬다.
오래된 걸 최신인 척하지 않는 게 요점이다.

시세를 못 받은 종목은 옛 RS 를 남기지 않고 **비운다** — 지난주 가격으로
선취매 판정이 내려지는 것보다 "모름"이 낫다. PER 도 저장된 `eps` 가 없고
되풀 수도 없으면 비운다.

```bash
python refresh_prices.py --selftest   # 네트워크 없이 17개 검사
```

**두 빌더는 같은 브랜치에 민다.** 동시에 돌면 뒤늦은 쪽이 push 거부를 당하는데,
그때 빌드 결과를 통째로 버리면 안 된다 — 실측으로 한국 빌드 #22 가 데이터를
다 만들어 놓고 push 거부 하나로 실패 처리됐다(그래서 `q_end` 가 안 들어왔다).
지금은 남의 커밋 위로 rebase 하고 최대 5회 재시도한다. 건드리는 파일이
데이터 하나뿐이라 충돌하지 않는다. 가짜 원격으로 경합을 재현해 확인했다.

## 선취매 후보를 뽑는 기준

한국·미국 **완전히 동일**하다(`tests/parity.mjs` 가 강제한다). 문턱값은
`GATE` 상수 한 곳에만 있다.

**1단계 · 모집단** — 가속과 분기 데이터가 있는 종목(가속 절댓값 150p 초과는 계산 오류로 제외)

**2단계 · 진짜 가속** — 아래를 모두 통과

| 조건 | 값 | 왜 |
|---|---|---|
| 가속 | > 0 | 레버리지가 지금 강해지는 중 |
| 매출 YoY(분기TTM 우선) | ≥ 0% | 매출이 줄면서 나오는 이익 레버리지는 비용절감이라 오래 못 간다 |
| 연간 스프레드 | ≥ 3p | 0 초과만 요구하면 +0.2p 짜리 무의미한 레버리지가 통과한다 |
| 분기TTM 스프레드 | ≥ 5p | 위와 같음 |
| 기저효과 | 아님 | 아래 참고 |

**3단계 · 아직 안 실림** — 52주 고점比 ≤ -12% **그리고** RS6M ≤ +5%.
그 전에 걸러지는 것: 냉각(정점 통과), 점화 직후(3M +20% 초과), 고점권.

**4단계 · 순위** — 네 축 가중합. 카드에 분해가 그대로 보인다.

| 축 | 배점 | 내용 |
|---|---:|---|
| 헤게모니 품질 | 50 | 분기TTM 스프레드 18 · 가속 12 · 매출 동반 12 · 추정치 방향 8 |
| 가격 미반영 | 30 | 52주 고점比 15 · RS6M 15 |
| 타이밍 | 10 | RS3M 등급 A/B/C |
| 밸류에이션 | 10 | PER. **일부러 낮게 묶었다** — 싼 데는 이유가 있을 수 있다 |

### 기저효과 판정에 매출을 결합한 이유

예전엔 분기 영업이익 YoY ≥ +50% 만으로 탈락시켰다. 그 그물에 NVDA(영익
+88%/매출 +71%), DELL(+65%/+39%), CLS(+85%/+47%) 처럼 **매출이 함께 폭증한**
종목이 걸렸다. 이익만 튀고 매출이 안 따라오는 게 기저효과지, 둘 다 튀면
진짜다. 그래서 매출 성장과 결합해서 판정한다 — 영익 +80% 이상은 매출 +40%를,
+50% 이상은 매출 +15%를 요구한다.

### 냉각 판정을 완화한 이유

예전엔 `RS6M > 0 && RS3M < 0` 이면 무조건 냉각이었다. 6개월 +4% / 3개월 -1%
같은 **단순 숨고르기까지** '정점 통과·뒷북 위험'으로 몰렸다. 지금은 충분히
오른 뒤 실제로 꺾였거나(RS6M > +10% 이고 RS3M ≤ -5%), 3개월이 6개월 대비
15p 넘게 나빠진 경우만 냉각으로 본다.

### 삭제하지 않고 분리하는 것들

- **축소형 레버리지**(매출 역성장) → 본 후보에서 빼되 **턴어라운드 구간**에
  따로 표시. 헤게모니는 아니지만 매출이 돌아서면 다른 얘기가 된다.
- **타이밍이 나쁜 종목**(RS3M ≤ -8%) → 삭제하지 않고 **C 등급**으로. 바닥은
  지나봐야 알기 때문이다. 등급은 '좋은 종목'이 아니라 '지금 들어가기 편한
  자리인가'를 뜻한다.

### 매출 방향이 어긋나면 그것을 보여준다

연간 매출과 최근 4분기(분기TTM) 매출이 다른 방향을 가리키는 종목이
**미국 401개 중 98개(24%)** 다. 예: CPB 는 연간 +6.4% 인데 최근 4분기는
-2.9% 다. 어느 한쪽만 보면 안 보이므로, 갈리면 `매출이 꺾이는 중 /
돌아서는 중` 으로 카드에 표시한다. 판정 자체는 더 최신인 분기TTM 을 쓴다.

### 적용 결과 (2026-08-08 데이터)

| | 모집단 | 진짜 가속 | 선취매 권역 | 타이밍 A/B/C | 턴어라운드 |
|---|---:|---:|---:|---|---:|
| 한국 (223종목) | 195 | 9 → **7** | 3 → **2** | 0/0/2 | 0 |
| 미국 (401종목) | 302 | 43 → **34** | 15 → **9** | 4/1/4 | 2 |

미국에서 가장 크게 바뀐 것: 직전 1위였던 **CPB 가 턴어라운드 구간으로**
내려갔다(최근 4분기 매출 -2.9%). 대신 기저효과 완화로 NVDA·DELL·CLS 등
9종목이 '진짜 가속' 목록에 복귀했다.

### 발표된 실적이 안 들어간 숫자는 후보로 올리지 않는다

**발견 경위.** 8/8 데이터에서 가속 양수 종목 **53개가 최근 3주 안에 실적을
발표**했다. 1위였던 MCK 는 데이터 기준일 **3일 전**에 발표했다. 그 실적이
우리 TTM 에 안 들어갔다면 카드의 스프레드·가속은 **지난 분기 이야기**인데
주가는 이미 새 실적에 반응한 뒤다 — "아직 안 움직인 것"을 찾는 도구가
정확히 반대편을 짚게 된다.

**판정 기준은 빌드 날짜가 아니라 분기말이다.** "최근 실적일 > 데이터 기준일"
로 비교하면 아무것도 안 걸린다(실측: 401종목 중 **0건**). 데이터 기준일은
빌드를 돌린 날이라 거의 항상 공시일보다 뒤이기 때문이다. 물어야 할 것은
"우리 TTM 이 그 실적을 담았는가" 이고, 그건 **우리 분기 데이터의 마지막
분기말**(`q_end`)로 판단해야 한다. 그래서 두 빌더가 `q_end` 를 기록한다.

| 판정 | 조건 | 처리 |
|---|---|---|
| `stale` | 공시가 우리 분기보다 **뒤의 분기**를 다룸(공시일−40일이 `q_end`보다 45일↑ 뒤) | **후보 제외** |
| `stale` | 공시일이 없어도 `q_end` 가 **135일↑** 낡음 | **후보 제외** |
| `due` | `q_end` 가 100~135일 — 분기는 끝났고 발표 임박·진행 중 | 통과 + 경고 |
| `fresh` | 최신 분기까지 반영됨 | 통과 |
| `unknown` | `q_end` 없음(옛 데이터) | 통과 + 미확인 표시 |

**문턱은 임의의 숫자가 아니라 공시 달력에서 유도한다.** 처음엔 135일로 뒀는데
그러면 **한국의 전형적인 사례를 놓친다** — yfinance 가 1분기까지만 주고
(`q_end` 3/31) 오늘이 8/8 이면 경과 130일이라 5일 차이로 안 걸린다. 그 시점에
시장은 이미 2분기 잠정실적을 봤다(7월 말). 그래서 이렇게 유도한다:

```
한 분기        91일
실적 공개까지   35일   ← 한국 잠정 25~35일 · 미국 8-K 20~40일
                       시장을 움직이는 건 '발표'지 '보고서'가 아니다
stale 문턱 = 91 + 35 = 126일   (다음 분기가 끝나고 그 실적도 공개됨)
due   문턱 = 91일              (분기는 끝났는데 아직 발표 전)
```

**한국은 실적 발표일을 아예 안 물어보고 있었다.** `d_until`·`ir` 에 `None` 을
하드코딩해둔 탓에, 미국은 8-K 날짜로 정밀 판정을 하는데 한국만 나이 기준
경로밖에 못 탔다. 이제 야후 `calendar` 에서 직전·다음 실적일을 받는다
(best-effort — 못 받으면 지금과 똑같이 `None` 이고 나이 기준으로 떨어진다).
덤으로 **한국판에서도 '실적 D-7 이내' 경고가 작동**한다.

`q_end` 를 기록하기 전에 만들어진 데이터에는 전환기 폴백이 있다 — 분기 시점을
모르더라도 **25일 안에 실적을 발표했으면** 반영 여부를 확인할 방법이 없으므로
후보에서 뺀다. 다음 빌드부터는 `q_end` 가 있으므로 이 경로를 타지 않는다.

### 삭제가 아니라 '실적 확인 필요' 구간으로

실측하니 한국 종목 **216/223 이 `q_end` = 2026-03-31** 이었다 — yfinance 가
아직 2분기를 안 줬다. 그래서 전 종목이 `stale` 이 되고 선취매 후보가 **0개**가
됐다. 판정은 맞지만 화면이 비어버린다.

매 분기 이런 구간이 생긴다:

```
2분기말 6/30 → 잠정실적 7월 말 → 분기보고서 8/14 → yfinance 반영 8월 중순~하순
                 └── 이 3~4주 동안 시장은 알고 우리는 모른다 ──┘
```

그래서 **삭제하지 않고 별도 구간으로** 뺀다(축소형을 턴어라운드 구간에 두는
것과 같은 원칙). 카드에 **어느 분기까지의 숫자인지** 적고, DART·10-Q 에서
최신 실적을 확인하라고 안내한다. 선취매 권역에는 올리지 않되, 분석 자체를
버리지는 않는다.

측정해보니 지연 판정으로 빠진 195종목 중 **실제로 후보였을 건 3개**뿐이었다.
화면이 통째로 비는 게 아니라 3개가 한 칸 아래로 내려간 것이다.

**순서가 중요하다.** 실적 반영 여부를 **가장 먼저** 본다. 숫자가 낡았으면 그
숫자로 내리는 어떤 분류도 못 믿기 때문이다 — 축소형인지 아닌지조차 모른다.
한때 `shrink` 를 먼저 봤더니 실적 발표 이틀 뒤인 MMS 가 낡은 매출로 '축소형'
판정을 받아 턴어라운드 구간에 그대로 올라왔다. `tests/stale.mjs` 가 이 경우를
회귀로 잡는다.

## 이 숫자가 언제 것이고 언제 바뀌는가 — 화면에 박아둔다

머리글에 **기준일**(수집한 날) · **경과**(오늘/어제/N일 전) · **다음 갱신
예정 시각**이 나온다. 시각은 보는 사람의 기기 시간대로 환산된다.

```
기준일 2026-08-08 [오늘]   수록 223종목 · 67개 세부산업
다음 갱신 8/9(일) 06:00
```

- 한국: 매주 **일요일 06:00 KST**
- 미국: 매주 **일요일 07:00 KST** (실패하면 같은 날 **19:00** 백업 슬롯)

**갱신이 밀리면 그 사실을 밝힌다.** 갱신 실패 회차는 직전 데이터가 그대로
남는데, 예정일만 보여주면 아무 일 없는 것처럼 보인다. 기준일이 8일을 넘기면
머리글에 `예정일이 지났는데 데이터가 그대로입니다` 가 붙는다.

화면의 일정표(`SCHED`)는 워크플로 cron 을 손으로 옮겨 적은 값이다. 한쪽만
고치면 화면이 조용히 거짓말을 하므로, `tests/freshness.mjs` 가 **워크플로
파일의 cron 을 직접 읽어 대조**한다. cron 을 바꾸고 화면을 안 고치면 CI 가 잡는다.

## 아이폰 홈 화면 웹앱 — 새로고침이 되게 만들어야 한다

standalone(홈 화면에서 실행)은 **주소창도 새로고침 버튼도 없고, 당겨서
새로고침도 안 된다.** iOS 는 앱을 잠재웠다 그대로 되살리므로 `loadData()` 가
다시 돌지 않는다. 주간 갱신 데이터를 다루는 도구에서 이건 **며칠 전 숫자를
계속 보는 것**과 같고, 사용자가 스스로 벗어날 방법이 없다.

세 겹으로 막는다.

1. **앞으로 돌아오면 스스로 다시 받는다** — `visibilitychange` 와
   `pageshow`(iOS 가 캐시에서 되살리는 경우). 다만 마지막 조회로부터 60초가
   안 지났으면 건너뛴다. 화면 전환할 때마다 요청이 나가면 안 된다.
2. **손으로 누를 버튼**(머리글 오른쪽 ↻) — standalone 에는 브라우저 크롬이
   없으니 이게 유일한 수단이다.
3. **캐시 지시** — `/data/*` 뿐 아니라 **HTML 자체도** `must-revalidate`.
   낡은 화면 코드가 캐시에 남으면 위의 1·2 조차 실려 있지 않은 옛 코드가 돈다.
   안 바뀌었으면 304 로 끝나므로 트래픽 부담은 없다.

`tests/webapp.mjs` 가 아이폰 없이 확인할 수 있는 부분을 본다 — 복귀 시 재조회,
최소 간격, `pageshow` 캐시 복원, 버튼, 캐시 헤더.

### 시계는 '시장 현지 시각'이다

머리글 오른쪽에 시계와 장 상태(장중 / 개장 전 / 장 마감 / 휴장)가 붙는다.
한국판은 **KRX 09:00–15:30**, 미국판은 **NYSE 09:30–16:00 ET** 기준이다.

시간대 변환은 `Intl.DateTimeFormat` 의 `timeZone` 으로 한다. 손으로 오프셋을
더하면 **미국 서머타임 전환 때 한 시간씩 틀린다.** 공휴일은 반영하지 않으므로
툴팁에 그렇게 적어뒀다.

화면이 가려지면 초침을 멈춘다 — 휴대폰에서는 그게 배터리다.

## 이 빌드가 하지 않는 것 (솔직하게)

- **외국인·기관 수급 미수집.** `pykrx` 가 KRX 계정(`KRX_ID`/`KRX_PW`)을 요구하도록
  바뀌어 자동 빌드에서 뺐다. 화면의 수급 배지·수급 보너스 토글은 데이터가 없으면
  **스스로 숨고**, AI 프롬프트는 "네이버 금융에서 직접 확인하라"고 지시한다.
  값이 채워지면 UI가 자동으로 다시 나타난다.
- **종목행 DART 자동 링크 없음.** 트레이드 카드의 DART 검색 링크로 대신한다.
- **한국 실적일은 야후가 절반만 준다(실측).** `calendar` 에서 받아오도록
  고쳤고 재보니 **다음 실적일 62/223(28%), 직전 실적일 15/223(7%)** 이다.
  다음 실적일이 있는 종목은 '실적 D-7 이내' 경고가 뜬다.
  **직전 실적일이 7% 라는 게 더 중요하다** — 실적 반영 지연 판정의 정밀 경로가
  이 날짜를 쓰기 때문이다. 즉 한국은 사실상 **나이 기준(126일) 하나로 판정**하고
  있고, 그래서 그 문턱을 공시 달력에서 정확히 유도하는 게 중요했다.
  미국은 8-K 날짜가 368/401(92%) 라 정밀 경로가 제대로 돈다.
- **컨센서스 추정치는 한국이 오히려 잘 채워진다(실측 190/223 = 85%).**
  "야후가 한국 종목엔 추정치를 잘 안 준다"고 적어뒀다가 실제로 재보니 틀렸다.
  분포도 정상이다 — 30일 변화율 중앙값 +0.6%, 상향 103·하향 80·보합 7.
  미국은 아직 못 쟀다: 추정치 수집이 들어간 뒤 돌린 회차가 SEC 차단으로
  가격층 부분 갱신 경로를 탔고, 그 경로는 추정치를 수집하지 않는다.
  비어 있으면 화면은 **중립**으로 처리한다 — 없다고 감점하지 않는다(PER
  결측에 감점을 줬다가 전 종목이 '밸류 미검증'으로 깎였던 전례가 있다).

## 알아둘 데이터 한계

- **분기 TTM 은 두 가지 모드다.** 야후가 8분기를 주면 전년 동기 TTM과 비교한
  정식 TTM YoY(`q_approx: false`). 4~7분기만 주면 **직전 회계연도 연간**과 비교한
  근사치이고 `q_approx: true` 로 표시되며, 트레이드 카드에 근사임을 알린다.
  실측하면 **한국 종목은 근사 모드가 절대 다수**(232종목 중 230)라 이것이 사실상
  기본값이다. 분기 손익을 아예 안 주는 종목은 `—`.
- **영업이익 정의 차이.** 야후의 `Operating Income` 이 DART의 K-IFRS 연결 영업이익과
  어긋날 수 있다. AI 프롬프트가 이 대조를 명시적으로 요구한다.
- **기저효과 이중 차단.** ① 전년 값이 0 이하거나 **10억원 미만**이면 계산에서 뺀다
  (원화 기준이라 미국판보다 자릿수가 크다). ② 그걸 통과해도 **매출 YoY ±300%,
  영업이익 YoY ±500%** 를 넘으면 버린다 — 미국판 `build_data.py` 와 같은 기준이다.
  이 상한이 없던 첫 빌드에서 스프레드 **+4472p** 가 나와 세부산업 중앙값까지
  오염됐다(보안서비스 +1307p). 두 규칙 모두 영업이익 기저에도 걸리므로 전년
  영업이익이 적자거나 미미한 종목(=흑자전환 스토리)은 목록에서 빠진다.
  남는 애매한 케이스는 화면이 처리한다: 가속 ±150p 초과는 회색 처리,
  영업이익 YoY +80% 이상 등은 '기저효과 추정'으로 TOP5 점수를 65% 깎는다.
- **우선주는 유니버스에서 뺀다.** 한국 종목코드 끝자리가 주식 종류를 뜻한다
  (0=보통주, 5/7/9=우선주, K/L=신형우선주). 우선주를 넣으면 ① 같은 회사가
  세부산업 중앙값에 두 번 들어가고(실측 22쌍) ② 재무는 회사 전체인데
  발행주식수는 우선주 물량이라 PER이 무너진다(실측 삼성물산우 0.13, LG우 0.27
  — 스코어러가 '저PER'로 오인해 가점까지 줬다).
- **PER 은 후행/선행이 섞인다.** 야후가 한국 종목의 `trailingPE` 도 `trailingEps` 도
  주지 않는다(실측 0/232). 그래서 **시가총액 ÷ 순이익**으로 후행 PER을 직접
  만든다(주가÷EPS 는 발행주식수 기준이 어긋날 수 있어 쓰지 않는다). 이렇게
  약 91%가 채워지고, 그래도 없으면 화면이 **선행(Forward) PER** 을 쓰며 숫자 뒤에
  `F` 를 붙인다 — 서로 다른 지표를 같은 것처럼 보이지 않게 하기 위해서다.
  계산된 PER 이 1 미만이거나 300 초과면 계산이 어긋난 것으로 보고 버린다.
  TOP5 스코어러의 저PER/고PER 기준선은 후행 PER 기준이라, 선행 PER로 대체된
  종목은 다소 관대하게 평가된다.
- **시세 오프린트·연휴 갭 방어.** 야후의 한국 시세에는 자릿수가 튄 값이 섞이고,
  설·추석 같은 긴 연휴가 끼면 며칠치 등락이 '하루'로 잡힌다. 그래서 ① 5일 롤링
  중앙값에서 35% 넘게 벗어난 점을 버리고 ② **연속 거래일(간격 4일 이내) 사이의
  등락만** 쓰고 ③ 지수 일간 ±15% 초과 수익률도 제외한다.
  이 처리 없이는 코스피 30일 실현변동성이 92.7%로 나왔다.

  **산출 근거를 데이터에 함께 싣는다** — `market.vol_moves` 에 최근 30거래일 일간
  최대 등락 5개가 들어가고, 화면 배지의 툴팁에 그대로 보인다.

  현재 값은 **75%** 이고 근거는 `[10.84, 8.95, 7.89, 6.37, 6.24]` 이다. 처음엔
  연휴 갭이 원인일 거라 보고 위 ② 필터를 넣었는데 **결과가 1도 안 바뀌었다** —
  최근 30거래일에 연휴가 없었고 저 등락들은 전부 연속 거래일에 실제로 찍힌
  값이다(가설이 틀렸다). 즉 남은 가능성은 "진짜 급등락 국면" 아니면 "야후
  `^KS11` 시세 자체의 계통 오류"인데, 여기서는 원본 시계열을 받을 수 없어
  가리지 못했다. **이 숫자는 아직 검증되지 않은 것으로 취급할 것.**
  다만 이 값은 상단 배지 표시용이며 **어떤 종목 점수에도 들어가지 않으므로**
  종목 판단에는 영향이 없다. 툴팁의 등락 목록을 보고 직접 판단하면 된다.
- **주간 스냅샷**이지 실시간이 아니다.

## 화면 — 증권사 리포트 양식

밝은 바탕에 **면과 선으로만** 구분한다. 어두운 배경에서 쓰던 그림자·글로우·
그라디언트는 흰 바탕에서 전부 지저분해지므로 걷어냈다.

- **머리글** — 제목 아래 굵은 선, 그 밑에 시장·벤치마크·회계기준·기준일·수록
  종목수. 부분 갱신 회차면 기준일에 `(가격만)` 이 붙는다.
- **섹션** — 아래 실선을 두른 제목. 카드가 아니라 표의 행처럼 읽히게 했다.
- **숫자 부호 색** — **양수 빨강 / 음수 파랑**. 한국 증시 표기 관례다.
  레이더 카드와 트레이드 카드가 같은 색을 쓴다 — 같은 숫자가 화면마다 다른
  색이면 그 색을 신뢰할 수 없게 된다.
- **판정 문구 색** — 숫자 색과 겹치지 않게 근거는 남색, 주의는 주황갈색.
  "이 빨강이 좋다는 뜻인지 나쁘다는 뜻인지" 헷갈리지 않게 분리했다.
- **본문 15px** 기준으로 전체를 약 1.16배 키웠다. 표·배지의 9~10px 글씨가
  50군데 넘게 있었다.
- 대비비는 전부 WCAG AA(4.5:1) 이상이다. 가장 낮은 것이 흐린 글씨 4.73:1.
- `@media print` 를 넣어 종이로 뽑아도 읽힌다 — 리포트니까.

아이콘 바탕은 흰색이 아니라 강조색인 남색이다. 흰 아이콘은 아이폰 홈 화면
(대개 사진 배경)에서 경계가 사라져 안 보인다.

## 테스트

```bash
python build_tree_kr.py --selftest     # 빌더 로직 + 출력 스키마

cd tests && npm install && npm test    # 두 페이지를 실제로 띄워 전 기능 클릭 + 파리티
```

`npm test` 는 세 가지를 돈다.

- **smoke_kr** — 결측(분기 없음·PER 없음·RS 없음)과 한글 매핑 없는 산업을 일부러
  섞은 합성 데이터로 돌려서, 빈 값을 만나도 화면이 깨지지 않는지 확인한다.
- **smoke_ux** — 두 페이지를 커밋된 실데이터로 띄워 팝업·설명·시장 전환·홈 화면
  추가·GPT 지침 일치를 확인한다.
- **webapp** — 아이폰 웹앱 동작(복귀 시 재조회·버튼·캐시 헤더)과 시계·장 상태.
- **freshness** — 기준일·다음 갱신 표시. 화면의 일정표가 워크플로 cron 과
  같은지 대조한다(어긋나면 화면이 거짓 안내를 하게 된다).
- **stale** — 실적 반영 지연 판정. 날짜 산수라 실데이터로는 확인이 안 된다
  (실데이터엔 지금 이 순간의 한 조합만 있는데 위험한 건 경계값이다). 각 경우를
  직접 심어서 확인한다 — 경계값 100일/135일 포함.
- **parity** — 한국판과 미국판의 **판정 로직이 갈라지지 않았는지** 확인한다.
  `priceIn`·`realAccel` 같은 시장 무관 함수는 주석을 뺀 본문이 완전히 같아야 하고,
  `scoreCandidate` 처럼 1차 자료 이름(DART vs 8-K)이 시장마다 달라야 하는 함수는
  문자열을 걷어낸 **문턱값·가감점 28개**가 같아야 한다. 한쪽만 고치고 다른 쪽을
  잊는 사고가 실제로 났기 때문에 붙였다(산업 레이더의 자루 버킷 제외가 한국판에만
  들어가 있었다). CI 는 `.github/workflows/tests.yml` 에서 같은 것을 돌린다.

## 면책

매수·매도 신호가 아니다. 목표가도 내지 않는다. 차트 가공지표(이동평균·RSI 등)는
일절 쓰지 않고 원시 비율만 쓴다. **"어디를 깊게 팔지" 좁히는 발견 도구**이지
매매 결정 도구가 아니며, 최종 판단은 1차 자료(DART)를 직접 읽고 내려야 한다.
